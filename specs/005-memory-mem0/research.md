# Research: 多代理記憶升級（Mem0）

## 決策 1：記憶供應採 Provider 抽象

### 決策

- 設計 `MemoryProvider` 介面，至少支持：`off`、`mem0_oss`、`mem0_platform`、`mock`。
- `chat.py` 僅依賴 `memory_service`，不直接引用 Mem0 SDK。

### 理由

- 降低第三方 SDK 對路由核心的耦合。
- 便於測試與故障回退。
- 後續可無痛切換供應器。

## 決策 2：採用三層長期記憶 Scope

### 決策

- `user_scope`: 使用者全域偏好。
- `agent_scope`: 代理專業經驗（不綁特定使用者）。
- `interaction_scope`: 指定 user + 指定 agent 的交叉偏好。

### 理由

- 對應多代理場景下的隔離與共享平衡。
- 可避免「記憶孤島」與「全域污染」兩種極端。

## 決策 3：短期記憶繼續 Redis，長期記憶交 Mem0

### 決策

- 短期記憶：Redis TTL + 最近 N 則會話訊息。
- 長期記憶：Mem0（底層向量庫使用 Qdrant）。

### 理由

- Redis 適合高頻讀寫與短 TTL。
- Mem0 提供長期記憶提取與 scope 管理能力。

## 決策 4：fail-open 降級為必要策略

### 決策

- 記憶檢索或寫回失敗時，聊天流程不得中斷。
- 失敗以事件與日誌記錄，回覆流程繼續。

### 理由

- 聊天可用性優先於記憶可用性。
- 生產環境需容忍外部依賴波動。

## 決策 5：長期記憶寫入由 Master gate 統一執行

### 決策

- Worker 不直接呼叫長期記憶寫入。
- Worker 回傳結果與錯誤線索後，由 Master/Orchestrator 統一決定是否與如何寫入。

### 理由

- 避免多 Worker 競態寫入與重複污染。
- 將隔離規則、敏感資訊過濾、去重策略集中在單點。
- 保持 Worker 無狀態與職責單純。

## 決策 6：記憶寫回分流規則

### 決策

- 使用者偏好類內容 -> `user_scope`。
- 代理修正經驗（工具錯誤、成功策略）-> `agent_scope`。
- 特定用戶在特定代理的要求 -> `interaction_scope`。

### 理由

- 避免把個資寫進共享專業記憶。
- 讓代理能累積可重用專業知識。

## 決策 7：與現有 RAG 功能解耦

### 決策

- 本功能不重構現有 RAG 上傳/檢索 API。
- 記憶上下文與 RAG 上下文在 prompt 層並存。

### 理由

- 降低一次改動風險。
- 可分階段驗收記憶與 RAG 能力。

## 決策 8：LiteLLM 閘道非硬依賴

### 決策

- Mem0 所需 LLM/Embedding 端點改由環境變數配置。
- 不假設本機一定存在 `:4000` 的 LiteLLM gateway。

### 理由

- 目前環境未必有 LiteLLM gateway 常駐。
- 避免部署時被固定埠口綁死。
