# 功能規格：腎友照護 POC（雙角色工作台 + S01/S02 + LINE）

**Feature Branch**: `009-renal-care`
**Created**: 2026-09-05
**Status**: Draft
**Input**: User description: "依據規格書、流程圖與展示站，完成腎友照護 POC 規格與工作項目。"

## 使用者情境與測試（必要）

### 使用者故事 1 - 護理師可在同一工作台管理四位病患（Priority: P1）

作為護理師，我希望在單一頁面快速掌握四位病患當班狀態、透析進度與異常追蹤。

**Why this priority**: 這是 POC 展示主軸，若無四人總覽就無法驗證工作台價值。

**Independent Test**: 護理師登入後，能切換六個左側選單頁並看到對應資料區塊。

**Acceptance Scenarios**:

1. **Given** 護理師進入工作台，**When** 檢視總覽，**Then** 可見床機配對、正常完成、追蹤件數、目標脫水完成率。
2. **Given** 護理師切換到異常追蹤，**When** 查看案件，**Then** 可見狀態、責任人與處理節點。

---

### 使用者故事 2 - 腎友/家屬可完成日常填報並收到非診斷性提醒（Priority: P1）

作為腎友/家屬，我希望在 LINE 或病患工作台完成日常填報，並看到可理解的提醒訊息。

**Why this priority**: 日常監測是 POC A 流程核心，必須打通填報到提醒閉環。

**Independent Test**: 送出早晚量測後，S01 成功寫入資料並回傳追蹤判定。

**Acceptance Scenarios**:

1. **Given** 使用者完成量測並確認送出，**When** 呼叫 S01，**Then** 回傳 `SAVED/REJECTED` 與比對結果。
2. **Given** 命中追蹤規則，**When** S01 完成比對，**Then** 建立主護追蹤任務並可於護理師端看到。

---

### 使用者故事 3 - 透析日流程可記錄洗前/中/後與異常事件（Priority: P1）

作為護理師，我希望在透析日完整記錄療程流程，並在異常時保留人工處理軌跡。

**Why this priority**: 透析流程是 POC B 流程核心，直接對應實務作業。

**Independent Test**: 建立透析 Session，寫入事件，完成洗後確認並查詢完整紀錄。

**Acceptance Scenarios**:

1. **Given** 建立透析任務，**When** 護理師確認床機與洗前資料，**Then** 可寫入並更新狀態。
2. **Given** 療程中發生異常，**When** 護理師處理，**Then** 系統記錄事件與處理人，不自動結案。

---

### 使用者故事 4 - 角色切換到腎友/家屬後顯示不同工作台（Priority: P2）

作為系統使用者，我希望上方「護理師 / 腎友家屬」切換後進入不同頁面與資料視角。

**Why this priority**: 參考站明確為雙角色體驗，需反映不同權限與資訊密度。

**Independent Test**: 兩角色入口分別導向獨立工作台，且資料可視範圍不同。

**Acceptance Scenarios**:

1. **Given** 點擊「護理師」，**When** 進入頁面，**Then** 可見四人管理功能。
2. **Given** 點擊「腎友/家屬」，**When** 進入頁面，**Then** 僅可見個人資料與任務。

## 邊界情境

- LINE webhook 到達但 payload 欄位不完整時，系統應拒絕或忽略，且不中斷服務。
- S01/S02 輸入缺少必要欄位時，必須回傳可理解錯誤，不可寫入半套資料。
- 異常事件建立後未完結時，不可被 AI 自動改為結案。
- 腎友/家屬角色不可看到其他病患資料。
- LINE 使用者已綁定為腎友後，訊息路由不可回退到一般聊天主代理。
- 腎友當日僅完成一次回報時，系統需可辨識為未完成每日兩次任務。
- 糖尿病腎友回報若缺血糖欄位，系統不可寫入 `SAVED`。

## 需求（必要）

### 功能需求

- **FR-001**: 系統 MUST 提供雙角色入口（護理師、腎友/家屬）與不同頁面。
- **FR-002**: 護理師工作台 MUST 含六個功能分頁：四人總覽、AI智慧照護、今日透析、個案趨勢、LINE對話、異常追蹤。
- **FR-003**: 系統 MUST 提供 S01（監測）API，支援輸入驗證、資料保存、規則比對與追蹤判定。
- **FR-004**: 系統 MUST 提供 S02（透析）API，支援 Session 建立、事件記錄、洗後確認。
- **FR-005**: 系統 MUST 保持 LINE 通道可用，支援 bot/human 模式與人工推送。
- **FR-006**: 系統 MUST 將所有關鍵資料落地並可被查詢追溯。
- **FR-007**: 系統 MUST 於醫療風險邊界保留人工確認節點。
- **FR-008**: 系統 MUST 避免 AI 自動診斷、醫囑下達與自動結案。
- **FR-009**: 腎友/家屬工作台 MUST 僅顯示本人授權範圍資料。
- **FR-010**: UI 視覺與互動 MUST 對齊參考展示站風格（資訊層級、配色語意、卡片佈局）。
- **FR-011**: 系統 SHOULD 支援腎友免註冊進入個人工作台（以 LINE 身分為主），並以短時效簽章機制完成身分驗證。
- **FR-012**: 免註冊模式下，系統 MUST 支援連結失效、重發連結與主動撤銷存取權。
- **FR-013**: LINE 來源且已綁定腎友之會話 MUST 固定由「腎友陪伴」代理處理，不經主代理二次分派。
- **FR-014**: 系統 MUST 檢核腎友每日需完成至少兩次監測（`MORNING` 與 `EVENING`），每次至少含血壓與體重。
- **FR-015**: 針對 `is_diabetic=true` 之腎友，系統 MUST 於日常監測要求血糖欄位，缺漏時回傳可理解錯誤。
- **FR-016**: 系統 SHOULD 提供可重用的提醒排程機制（政策、任務、投遞記錄）以支援催報與補報通知。

### 關鍵實體

- **RenalPatient**: 病患主檔（POC 四位虛構病患）。
- **MonitoringRecord（S01）**: 日常監測記錄與比對結果。
- **DialysisSession（S02）**: 透析單次療程主檔。
- **DialysisEvent（S02）**: 透析中事件與處理紀錄。
- **FollowUpCase**: 主護追蹤案件。
- **LineChannelSession / LineMessage**: LINE 通道會話與訊息稽核。

## 成功指標（必要）

### 可量測成果

- **SC-001**: 護理師工作台六分頁可切換且資料載入成功率 >= 99%（POC 測試環境）。
- **SC-002**: S01/S02 核心流程端到端測試全數通過。
- **SC-003**: LINE 日常填報與人工接手流程可完整演示，成功率 >= 95%。
- **SC-004**: 所有異常處理都具備人工操作人與時間戳記，覆蓋率 100%。
- **SC-005**: 角色隔離測試中，腎友/家屬越權存取為 0。
- **SC-006**: 腎友從 LINE 進入網頁的免註冊登入成功率 >= 95%（POC 測試環境）。
- **SC-007**: LINE 腎友訊息由「腎友陪伴」代理處理占比 100%，且無主代理誤路由事件。
- **SC-008**: 連續 7 天模擬資料中，每日兩次回報完整性檢核正確率 100%。
- **SC-009**: 糖尿病腎友缺血糖欄位請求之攔截率 100%，且錯誤訊息可被前端直接顯示。
