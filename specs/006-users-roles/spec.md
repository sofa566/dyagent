# 功能規格：User / Group / Role 動態權限管理

**Feature Branch**: `006-users-roles`  
**Created**: 2026-07-30  
**Status**: Draft  
**Input**: User description: "補齊使用者、群組、角色的建立/編輯；採 B 模式（User 與 Group 皆可多對多掛載 Role）；登入後介面即時顯示可執行功能，無權限功能不可見。"

## 使用者情境與測試（必要）

### 使用者故事 1 - 管理者可建立並調整角色（Priority: P1）

作為系統管理者，我希望可以建立、編輯、停用角色，並隨時調整角色對應的功能權限。

**Why this priority**: 角色不可建立/編輯會直接阻斷整個授權模型落地。

**Independent Test**: 建立新角色並指派權限後，使用該角色的帳號可立即看見對應功能入口。

**Acceptance Scenarios**:

1. **Given** 管理者建立 `skill_manager` 角色且授予 `skills.read`、`skills.update`，**When** 使用者被指派該角色登入，**Then** 技能管理頁面入口可見且可操作。
2. **Given** 管理者移除 `skills.update`，**When** 同一使用者重新載入頁面，**Then** 編輯按鈕立即隱藏且更新 API 呼叫被拒絕。

---

### 使用者故事 2 - 使用者與群組皆可多對多掛載角色（Priority: P1）

作為管理者，我希望能同時透過「使用者直掛角色」與「群組繼承角色」管理權限，以降低大量帳號維運成本並保留彈性。

**Why this priority**: 這是本次指定的 B 模式核心，且直接影響授權可擴充性。

**Independent Test**: 同一使用者同時掛載 1 個直掛角色與 1 個群組角色，最終權限為聯集。

**Acceptance Scenarios**:

1. **Given** user_A 直掛 `report_viewer`、所屬群組 `ops_group` 掛載 `agent_editor`，**When** user_A 查詢自身能力，**Then** 權限集合包含兩角色聯集。
2. **Given** user_A 被移出 `ops_group`，**When** 再次查詢能力，**Then** 僅保留直掛角色對應權限。

---

### 使用者故事 3 - 登入後操作介面即時反映可用功能（Priority: P1）

作為一般使用者，我希望登入後只看到我能使用的功能，避免誤點無權限頁面。

**Why this priority**: 降低誤操作與支援成本，並符合最小權限原則。

**Independent Test**: 修改使用者權限後，不需重新登入即可在前端重新拉取能力並更新可見功能。

**Acceptance Scenarios**:

1. **Given** 使用者已登入，**When** 管理者在後台移除其某項權限，**Then** 使用者刷新或切回頁面後該功能入口立即消失。
2. **Given** 使用者沒有 `users.read`，**When** 進入系統，**Then** 導覽列與頁面入口不顯示使用者管理。

---

### 使用者故事 4 - 後端授權為最終防線（Priority: P2）

作為安全管理者，我希望即使前端被繞過，後端仍能依實際權限拒絕未授權操作。

**Why this priority**: 前端隱藏僅是體驗層，安全必須由後端保證。

**Independent Test**: 使用無權限帳號直接呼叫受限 API，應回應 403。

**Acceptance Scenarios**:

1. **Given** 使用者缺少 `roles.update`，**When** 直接呼叫角色更新 API，**Then** 回應 403。
2. **Given** 使用者缺少 `groups.delete`，**When** 嘗試刪除群組，**Then** 回應 403 並記錄稽核事件。

## 邊界情境

- 使用者同時擁有多個角色且權限重疊時，權限去重後應一致且無順序依賴。
- 角色停用後，所有透過該角色取得的權限應立即失效（含群組繼承與直掛）。
- 管理者不得刪除系統保留角色（例如初始超級管理角色），除非完成替代保護流程。
- 權限鍵不存在或拼字錯誤時，系統不得默默放行，需明確拒絕或驗證失敗。
- 當能力快取存在時，角色異動需有失效機制，避免前端顯示與後端判斷不一致。

## 需求（必要）

### 功能需求

- **FR-001**: 系統 MUST 提供 `Role` 的建立、編輯、停用、查詢功能。
- **FR-002**: 系統 MUST 提供 `Group` 的建立、編輯、停用、查詢功能。
- **FR-003**: 系統 MUST 支援 `User ↔ Role` 多對多關係（直掛角色）。
- **FR-004**: 系統 MUST 支援 `Group ↔ Role` 多對多關係（群組角色）。
- **FR-005**: 系統 MUST 支援 `User ↔ Group` 多對多關係（使用者可加入多群組）。
- **FR-006**: 系統 MUST 以「使用者直掛角色 + 使用者所屬群組角色」聯集計算有效權限。
- **FR-007**: 系統 MUST 提供查詢目前登入者能力的 API（至少包含 roles、groups、permissions）。
- **FR-008**: 前端 MUST 依能力 API 動態顯示功能入口，無權限功能不可見。
- **FR-009**: 後端 MUST 在每個受保護 API 上以權限鍵做授權驗證，不得僅依前端控制。
- **FR-010**: 角色權限異動後，已登入使用者 MUST 可在重新載入頁面後立即看到新能力。
- **FR-011**: 系統 MUST 保留現有使用者角色欄位的遷移相容策略（過渡期間可雙軌）。
- **FR-012**: 系統 MUST 提供稽核紀錄（誰在何時變更了角色/群組/指派關係）。

### 關鍵實體

- **Permission**: 權限鍵定義（如 `skills.read`、`skills.update`、`users.read`）。
- **Role**: 可被指派的角色，包含名稱、代碼、狀態與權限集合。
- **Group**: 使用者群組，包含名稱、代碼、狀態與綁定角色集合。
- **UserRoleBinding**: 使用者與角色多對多關係。
- **GroupRoleBinding**: 群組與角色多對多關係。
- **UserGroupBinding**: 使用者與群組多對多關係。
- **EffectivePermissionSet**: 依目前綁定關係計算後的最終權限聯集。

## 成功指標（必要）

### 可量測成果

- **SC-001**: 角色/群組管理功能（建立、編輯、指派）主要流程測試通過率達 100%。
- **SC-002**: 權限異動後，前端於重新載入或頁面切換後 3 秒內完成可見功能更新。
- **SC-003**: 無權限使用者對受保護 API 的攔截率 100%（全部回 403）。
- **SC-004**: 多對多聯集授權測試（User+Group 組合）100% 通過且無權限遺漏/超發。

## 設計決策備註

- 本功能採 **B 模式**：`User ↔ Role`、`Group ↔ Role` 皆為多對多，且 `User ↔ Group` 亦為多對多。
- 「看不到功能」屬前端體驗策略；真正授權必須由後端權限檢查保證。
