# 006-users-roles 變更計畫（角色/群組各自綁定權限）

## 目標

將授權模型調整為：

- 角色可直接綁定權限
- 群組可直接綁定權限
- 角色與群組互不綁定
- 使用者最終權限為聯集（allow-only）

最終權限公式：

`使用者權限 = 使用者角色權限聯集 + 使用者群組權限聯集`

---

## 分階段執行

### 階段 1：資料模型與權限計算核心（本次開始）

完成項目：

1. 新增資料表 `group_permission_bindings`（`group_id + permission_id` 唯一）。
2. 新增 ORM model `GroupPermissionBinding`。
3. 調整 `resolve_effective_capability`：
   - 載入使用者群組
   - 取群組直掛權限
   - 與角色來源權限做聯集
4. 單元測試覆蓋：
   - 使用者可僅靠群組直掛權限取得能力
   - 與角色權限同時存在時結果為聯集

驗收標準：

- 不依賴「群組->角色」也可生效。
- 既有角色權限行為不被破壞。

### 階段 2：後端 API（群組權限綁定）

完成項目：

1. 新增 `GET /access/groups/{group_id}/permissions`。
2. 新增 `POST /access/groups/{group_id}/permissions`（replace 模式）。
3. 增加稽核事件 `group_permission.replace`。

驗收標準：

- 能讀寫群組直掛權限。
- 權限更新可即時反映在 `me/capabilities`。

### 階段 3：前端 access-control 整合

完成項目：

1. 在綁定管理加入「群組直掛權限」樹狀清單。
2. 保留現有角色管理與使用者綁定流程。
3. 顯示「最終權限為聯集」提示。

驗收標準：

- 勾選、儲存、重載回填一致。
- 管理者可在同頁完成群組權限配置。

### 階段 4：治理與可追溯性

完成項目：

1. 能力檢視提供「權限來源」資訊（role/group）。
2. 建立管理規範與盤點流程（避免配置漂移）。
3. 提供簡化的權限解釋資訊（為何某人有某權限）。

驗收標準：

- 能回答「誰、為何、從哪裡得到此權限」。
- 維持可維護、可稽核、可逐步收斂。

## 風險降低策略（不增加太多複雜度）

### 1) 僅 allow，不引入 deny

原因：deny 會引入優先序、衝突規則與維護負擔。

做法：只要任何來源授權，即視為可用。

效益：邏輯可預測、實作成本低、除錯簡單。

### 2) 顯示權限來源（role / group）

原因：多來源聯集最怕「授權來源不透明」。

做法：在能力檢視中標註每個權限來自角色或群組。

效益：管理者可快速定位授權來源，降低誤判。

### 3) 群組直掛權限可用，但需規範與定期清理

原因：直掛方便但容易累積技術債。

做法：定義命名規範與定期盤點，把長期規則回收為角色模板。

效益：兼顧效率與治理，避免配置膨脹。

### 4) 提供權限解釋（Permission Explain）

原因：稽核與問題排查需要可追溯證據。

做法：可先提供文字版來源說明，不強求複雜圖形化。

效益：低成本提升可治理性與可維運性。
